# Output and classifications

All artifacts are flat under `--output-dir` (`$HOME/overclock-results` by default); no per-target directories are created and existing runs are never deleted. Prepare and overclock operations record their effective `.conf`, discovery snapshot, atomic `.state`, `.log`, `.csv`, `.jsonl`/`.json`, and summary; overclock also records per-candidate logs. A reset records its own atomic state and audit output without manufacturing a tuning configuration or candidate logs. The `*-latest.log`, `*-latest-summary.txt`, `*-latest.state`, and `*-latest.json` links select the latest retained operation for a target.

`reset` creates a separate audit run instead of reusing or deleting tuning history. Previous run files remain byte-preserved even when the target's `*-latest` links advance to the reset audit. A successful reset state ends at `COMPLETE/STOCK_VERIFIED` and records the verified pre-reset hash, post-reset hash, persistent remote config-backup path, and disabled-key evidence. When attributable project tryboot evidence required cleanup, its backup path is recorded separately. The final `reset` PASS event reports that a new permanent-config boot reached verified firmware stock defaults and that prior logs and saved runs were preserved.

| Classification | Meaning |
|---|---|
| `PREFLIGHT_FAILURE` | Unsupported/missing prerequisite before tuning. |
| `HARNESS_FAILURE` | The intended test did not actually run or prove its workload, including an unstructured same-boot transport loss. |
| `BOOT_FAILURE` | Candidate boot or required display/audio/service health failed. |
| `STABILITY_FAILURE` | Power, temperature, kernel, GPU, storage, filesystem, or stress failure, including a proven autonomous candidate reboot during active stress. |
| `RECOVERY_FAILURE` | The target did not return to verified permanent normal configuration. |
| `APPLY_FAILURE` | Permanent application or rollback failed. |

The `.state` file is data-only: sorted uppercase keys with base64-encoded values. It is never sourced. The `.jsonl` event stream is finalized into a JSON array when the controller exits.

Clock results are intentionally separate: `PASSED_CPUS`/`PASSED_GPUS` record observed sweep/refinement passes; `CPU_FAILURE_BOUNDARY`/`GPU_FAILURE_BOUNDARY` retain the first refined edge; `CPU_GUARD_TARGET`/`GPU_GUARD_TARGET` record tested production guards; and `FINAL_CPU`/`FINAL_GPU` remain empty until full validation completes. `FINAL_BACKOFF_COUNT`, `FINAL_BACKOFF_CPU`, `FINAL_BACKOFF_GPU`, and the ordered `FINAL_BACKOFF_HISTORY` bind any recovered domain-specific final-stress boundaries to monotonically reduced validation targets. Optional edge mode additionally records `FLOOR_*` evidence and `EDGE_CPU_*` status so a recovered edge rejection can retain the validated floor without being confused with an edge pass.

`RUN_SCHEMA` prevents an older interrupted state from bypassing newer resume gates. `AUTO_BASELINE_*` preserves the immutable stock tuple and provenance even after a successful apply updates the live normal clocks. `CANDIDATE_LABEL`, candidate clocks, and `CANDIDATE_STAGE` identify the exact recoverable candidate substage. `FINAL_TARGET_CPU`, `FINAL_TARGET_GPU`, and `FINAL_STAGE` do the same for final validation. `VALIDATION_SCHEMA` and `VALIDATION_DURATION_S` are recorded only when final validation completes and are both required by `apply`; an optional edge pass must carry 86,400 seconds rather than the ordinary 28,800-second floor.

A later edge run sets `POST_FLOOR_EDGE=1` and binds `SOURCE_FLOOR_RUN_ID` plus `SOURCE_FLOOR_PERMANENT_HASH` to its retained source. Its own run ID keeps apply and rollback artifacts separate, while `MODE_EFFECTIVE` and `REQUIRE_GPU_STRESS` preserve the proven graphical or headless path. `CFG_MAX_FAN` records whether candidate tryboots use the default maximum-cooling block (`1`) or the explicit `--no-max-fan` policy (`0`); status, report, summary, and effective-config comments expose that choice, and resume retains it.

Graphical runs store `DISPLAY_BASELINE` and the discovered `AUDIO_BASELINE`, and both identities are required on subsequent candidate, normal-recovery, and apply health checks. Debian prefers an active PipeWire/PulseAudio default-sink identity and otherwise records the sorted complete ALSA playback inventory, so a missing desktop audio session does not disable audio validation or force the controller to guess one device. A configured `audio_sink_pattern` still requires a matching desktop sink. Batocera graphical runs require its active default-sink identity. Discovery also records `FAN_PWM_STATUS`; with default maximum cooling, candidate health and every stress telemetry sample report PWM/RPM proof when Linux exposes the Pi `pwmfan` device. `--no-max-fan` records the normal policy without making a PWM-255 claim. `not-detected` is retained as an honest absence of software fan evidence, not reported as 100%. Watchdog discovery records the EEPROM timeout, active kernel handoff, device, live timeout, and owner. A Debian repair additionally records its status, old/expected/new hashes, and backup path so an interrupted `PREPARE` report does not conceal a partial change.

Interrupted apply state records `APPLY_OLD_HASH`, `APPLY_EXPECTED_HASH`, a deterministic `APPLY_BACKUP`, boot evidence, and the intended recovery action. Reconciliation accepts only the known old or proposed hash; an unknown permanent hash is left untouched for manual recovery.
