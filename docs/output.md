# Output and classifications

All artifacts are flat under `--output-dir` (`$HOME/overclock-results` by default); no per-target directories are created and existing runs are never deleted. Prepare, overclock, and manual test operations record their effective `.conf`, discovery snapshot, atomic `.state`, `.log`, `.csv`, `.jsonl`/`.json`, and summary; overclock and test also record per-candidate logs. A reset records its own atomic state and audit output without manufacturing a tuning configuration or candidate logs. The `*-latest.log`, `*-latest-summary.txt`, `*-latest.state`, and `*-latest.json` links select the latest retained operation for a target. The JSON array is synthesized from `.jsonl` when the controller exits through its cleanup handler, so the `.json` target may not exist while a run is active or after an uncatchable process kill. The atomic `.state`, `.jsonl`, log, and summary remain the continuation evidence; a missing live JSON file does not mean the run state was lost.

`report TARGET --redact` writes `autopioverclock-RUN_ID-public-report.txt` rather than a target-slug filename. It replaces known target/controller identifiers and omits free-form failure/backoff reasons and storage layout because those fields can contain arbitrary paths, service names, addresses, or device identities. Review even this reduced report before publication; raw artifacts are not share-safe.

Artifact destinations are reconstructed from the selected, filename-validated state path rather than trusted from redundant state values. `status` and `summary` are read-only observers: they inspect the existing controller lock and send a transient worker over SSH for a short live clock/config/health snapshot without installing it or acquiring the controller lock. They do not change boot configuration or project run artifacts; ordinary SSH/sudo service logging can still occur. `status` defaults to the latest operation; `summary` defaults to the newest tuning/manual-test state so later prepare, reset, and restore audits do not hide the tuning story. `report` reads its selected local snapshot and writes only its requested report file. Observer exit handling never finalizes run JSON, changes state, invokes recovery, or cleans a worker.

`reset` creates a separate audit run instead of reusing or deleting tuning history. Previous run files remain byte-preserved even when the target's `*-latest` links advance to the reset audit. A successful reset state ends at `COMPLETE/STOCK_VERIFIED` and records the verified pre-reset hash, post-reset hash, persistent remote config-backup path, and disabled-key evidence. When attributable project tryboot evidence required cleanup, its backup path is recorded separately. The final `reset` PASS event reports that a new permanent-config boot reached verified firmware stock defaults and that prior logs and saved runs were preserved.

| Classification | Meaning |
|---|---|
| `PREFLIGHT_FAILURE` | Unsupported/missing prerequisite before tuning. |
| `HARNESS_FAILURE` | The intended test did not actually run or prove its workload, including missing/changed required audio readiness, a structured harness diagnosis, or unstructured same-boot transport loss after five safely recovered automatic retries are exhausted. |
| `BOOT_FAILURE` | Candidate boot or required boot/display/service health failed, including an exactly observed autonomous reboot during that gate after full normal recovery. |
| `STABILITY_FAILURE` | Power, temperature, kernel, GPU, storage, filesystem, stress, or post-stress-health failure, including an exactly observed autonomous candidate reboot after full normal recovery. |
| `RECOVERY_FAILURE` | The target did not return to verified permanent normal configuration, or protected recovery evidence remained unavailable/mismatched after its retry policy. An older controller-only unavailable-hash result may be normalized to `HARNESS_FAILURE` only after fresh stock health and the exact hash are re-proved. |
| `APPLY_FAILURE` | Permanent application or rollback failed. |

The `.state` file is data-only: sorted uppercase keys with base64-encoded values. It is never sourced. The `.jsonl` event stream is finalized into a JSON array when the controller exits.

Clock results are intentionally separate: `PASSED_CPUS`/`PASSED_GPUS` record actual sweep/refinement passes; `CPU_FAILURE_BOUNDARY`/`GPU_FAILURE_BOUNDARY` retain observed failures; and `FINAL_CPU`/`FINAL_GPU` remain empty until full validation completes. `CPU_QUALIFICATION_*` and `GPU_QUALIFICATION_*` bind each required saved-duration qualification to its exact CPU/GPU pair, including the held verified/applied clock in one-domain mode. Final backoff state and ordered history bind each failed-pair anchor and its CPU-only, GPU-only, or paired 25 MHz isolation trial. A successful single-domain trial preserves the other domain's anchor clock; only after both isolated trials fail is the paired reduction tested and eligible to become the next lower anchor. One-domain mode keeps the held clock and records only its selected-domain reduction.

`RUN_SCHEMA` prevents an older interrupted state from bypassing newer resume gates. Current public state binds the immutable qualification/final durations, selected domain mode, optional ladder starting points, and cooling policy. `AUTO_BASELINE_*` preserves the immutable stock tuple and provenance even after a successful apply updates the live normal clocks. `CANDIDATE_LABEL`, candidate clocks, and `CANDIDATE_STAGE` identify the exact recoverable candidate substage; `FINAL_TARGET_CPU`, `FINAL_TARGET_GPU`, and `FINAL_STAGE` do the same for final validation. Individual transient reads receive 30 validated attempts, safe same-boot worker gates receive up to five attempts, and `TRANSIENT_RETRY_CONTEXT`/`TRANSIENT_RETRY_COUNT` bind five automatic complete-gate repeats to one exact safely recovered harness boot, stress, or health gate. `VALIDATION_SCHEMA` and `VALIDATION_DURATION_S` are recorded only when final validation completes and are both required by `apply`; the duration must exactly equal the saved final duration. Time from a failed final attempt is retained only as forensic evidence and is never accumulated toward a later attempt.

A standalone validated-config restore writes a separate audit with `ORIGIN_COMMAND=restore`, the selected `RESTORE_SOURCE_RUN_ID` and source hash, the replaced config hash and deterministic backup, and final `RESTORE_STATUS=VERIFIED`. It does not alter the source run or its retained validation artifacts.

A longer final restart records its source run/hash/backup, rolls back only through that verified backup, and reapplies only after the linked validation passes. Each linked run ID keeps apply and rollback artifacts separate, while `MODE_EFFECTIVE` and `REQUIRE_GPU_STRESS` preserve the proven graphical or headless path. `CFG_MAX_FAN` records whether candidate tryboots use the default maximum-cooling block (`1`) or the explicit `--no-max-fan` policy (`0`); status, report, summary, and effective-config comments expose that choice, and resume retains it.

A manual exact-clock record has `ORIGIN_COMMAND=test`, `MANUAL_TEST=1`, `MANUAL_CPU`, `MANUAL_GPU`, `MANUAL_MINUTES`, `MANUAL_DURATION_S`, and a `MANUAL_TEST_STATUS` of `READY`, `RUNNING`, `PASS`, or `FAILED`. A pass deliberately retains `VALIDATED=0`, empty validation-schema/endurance fields, and `APPLY_STATUS=NOT_APPLIED`; it is evidence for that explicit test condition, not an application candidate. `RUN_MAX_TEMP` retains the highest structured worker temperature seen across the run.

`PROGRESS_ACTIVE_SECONDS` checkpoints active controller time across safe continuation. `PROGRESS_STRESS_*` records the current timed workload and its latest worker elapsed/duration counters, while `PROGRESS_LAST_*` caches clocks, temperature, throttle, and fan telemetry for display. `RECOVERY_WAIT_*` records when an unattended public overclock exceeded its ordinary SSH budget and entered extended read-only monitoring. These fields support operator visibility; they do not replace raw evidence. Every worker line, including telemetry with `elapsed=SECONDS/TOTALs`, remains in the per-attempt and main logs. Noninteractive output also prints those raw lines directly. A signal clears and disables only the advisory display while the exit trap continues to log required recovery evidence.

Graphical runs store `DISPLAY_BASELINE` and the discovered `AUDIO_BASELINE`, and both identities are required on subsequent candidate, normal-recovery, and apply health checks. Debian prefers an active PipeWire/PulseAudio default-sink identity and otherwise records the sorted complete ALSA playback inventory, so a missing desktop audio session does not disable audio validation or force the controller to guess one device. A configured `audio_sink_pattern` still requires a matching desktop sink. Batocera graphical runs require its active default-sink identity. Missing or changed audio readiness by itself is a retryable `HARNESS_FAILURE`, not a CPU/GPU clock boundary. Headless Debian-family runs intentionally retain empty display/audio baselines and instead record `DRM_RENDER_NODE` plus `STRESS_NG_GPU_STRATEGY`; the strategy is either exact V3D-device selection or the verified single-V3D-node fallback. Discovery also records `FAN_PWM_STATUS`; with default maximum cooling, candidate health and every stress telemetry sample report PWM/RPM proof when Linux exposes the Pi `pwmfan` device. `--no-max-fan` records the normal policy without making a PWM-255 claim. `not-detected` is retained as an honest absence of software fan evidence, not reported as 100%. Watchdog discovery records the EEPROM timeout, active kernel handoff, device, live timeout, and owner. A Debian repair additionally records its status, old/expected/new hashes, and backup path so an interrupted `PREPARE` report does not conceal a partial change.

Interrupted apply state records `APPLY_OLD_HASH`, `APPLY_EXPECTED_HASH`, a deterministic `APPLY_BACKUP`, boot evidence, and the intended recovery action. Reconciliation accepts only the known old or proposed hash; an unknown permanent hash is left untouched for manual recovery.
