# Safety and failure policy

AutoPiOverclock optimizes for recoverability and long-term stability rather than the highest benchmark number.

A candidate fails immediately on any current-boot undervoltage/throttle flag, thermal ceiling event, V3D/DRM fault, kernel panic/internal error/unable-to-handle-kernel report, Oops/BUG/call trace, RCU stall/starvation/timer failure, hung-task warning, USB-device reset, device-offline event, I/O error, buffer error, ext4/btrfs error, nonzero stress process, missing renderer proof, required graphical/audio/service failure, watchdog-chain failure, unexpected reboot, or permanent-config hash change.

`BOOT_FAILURE` and `STABILITY_FAILURE` define a sweep boundary. A lower passing candidate can still proceed to conservative selection. `HARNESS_FAILURE` and `RECOVERY_FAILURE` abort the run because they do not establish a silicon stability boundary.

A lost SSH stream is not itself a stability boundary. When active stress ends without a structured worker result, the controller promotes the fallback from `HARNESS_FAILURE` to `STABILITY_FAILURE` only if verified recovery first observes that the exact saved candidate boot ID has already changed to a clear permanent-normal boot before the controller issues any reboot. A same-boot transport interruption remains `HARNESS_FAILURE`, and any failure to verify normal recovery remains `RECOVERY_FAILURE`.

A maximum observed pass is never called “rock solid.” Configuration-free auto refines the failure gap at 25 MHz, then candidate-tests a production clock 50 MHz below the CPU boundary and 25 MHz below the GPU boundary. If ordinary final CPU-only or GPU-only stress still proves a stability failure and complete normal recovery succeeds, auto lowers only that domain by the same 50 MHz or 25 MHz guard. If combined endurance proves only that the pair failed, auto conservatively lowers every still-overclocked domain by its corresponding guard and explicitly makes no causal attribution. Each backoff is monotonic and restarts the entire final validation. Boot, harness, or recovery failures remain fatal uncertainty, and paired backoff is not used for the optional edge experiment. Explicit plans retain their configured list-position backoff. Final clocks are recorded only after CPU-only validation, GPU-only validation whenever GPU load is required, combined endurance, filesystem activity, post-stress health, the configured `final_boots` additional candidate boots and normal recoveries, and a final permanent-config hash check. The approved floor is three final boot/recovery cycles.

The 3200 MHz CPU and 1200 MHz GPU/V3D limits are sweep ceilings, not safe recommendations or promises that a target can boot them. Configuration-free auto refuses to generate candidates unless the active Pi 5 tuple is CPU 2400 MHz, V3D 800 or 960 MHz, and zero voltage delta, and a before/after-hashed audit of the permanent root config finds no explicit clock or voltage control. This covers boost/turbo/fixed-clock controls, every `*_freq`/`*_freq_min` assignment, and every `over_voltage*` assignment. Any snapshot change or `include` directive fails closed because unbound content cannot prove the protected baseline. Existing overclocks and unknown defaults fail preflight. Candidate clocks remain temporary; only the final current-schema result is written permanently by the explicit `overclock` command after complete validation and fresh apply gates. Tryboot recovery and every normal stability boundary remain mandatory.

Candidate cooling is isolated to the same temporary artifact. The candidate file inherits the complete protected permanent config—preserving unrelated GPU drivers, overlays, display, audio, PCIe, and other boot requirements—and adds only the project-owned clock/cooling block. By default, every candidate and final-validation tryboot sets the Pi 5 first fan threshold to 0C and all four fan speeds to PWM 255. The worker verifies a detected `pwmfan` device at 255 before health/stress and at every stress telemetry interval; a non-max value, malformed reading, or exposed zero-RPM tachometer is `HARNESS_FAILURE`, never a clock boundary. A missing software-visible PWM device is recorded as `not-detected` so passive and externally controlled cooling remain usable without a false 100% claim. `--no-max-fan` is an explicit new-run opt-out that retains the ordinary fan policy and disables only the PWM-255 assertion; temperature, throttle, clock, and workload gates remain unchanged. The selected policy is persisted and cannot change during resume. Normal recovery, permanent apply, and reset retain the pre-existing permanent fan directives unchanged.

Manual `test TARGET --cpu ... --gpu ... --minutes ...` uses the same candidate ownership, watchdog, maximum-cooling, boot-cycle, health, hash, and normal-recovery gates for one exact clock pair. Both clocks must be normal-or-higher and at least one must be an overclock. A manual pass remains `VALIDATED=0`, creates no conservative recommendation, and is explicitly ineligible for permanent apply even when the requested duration is eight hours or longer. This prevents a user-selected point from bypassing sweep boundaries, guarded selection, domain-specific final stress, combined endurance, and final post-stress boot requirements.

The interactive progress display is advisory only. Whole-workflow percentage, ETA, and remaining-test counts re-plan from saved phase/index/boundary evidence and never mark a safety gate complete. Worker-reported current-stress elapsed time drives the per-workload countdown; raw telemetry is retained independently. Progress rendering is disabled for non-TTY output so logs and automation receive ordinary newline-delimited evidence rather than terminal-control updates. Signal and exit handling clear the display and suppress any repaint while mandatory normal recovery is running.

Optional `--edge-cpu-24h` runs only after the ordinary 50 MHz-buffered CPU production floor has completed its full eight-hour validation. It then raises only CPU by 25 MHz and repeats the complete validation with 24-hour endurance. The flag may also be invoked later: only a current-schema `PASS`/`COMPLETE`/`VALIDATED=1` 28,800-second floor that was already applied is eligible, and the controller must freshly prove its exact permanent hash, normal clocks, clear tryboot state, watchdog health, and saved graphical/headless mode. The later run has a new identity and rollback backup and never rewrites the source evidence or repeats its eight-hour endurance. A recovered `BOOT_FAILURE` or `STABILITY_FAILURE` rejects the experiment while preserving the validated floor. `HARNESS_FAILURE` or `RECOVERY_FAILURE` remains fatal because it does not establish an edge boundary safely.

## Tryboot file ownership and cleanup

An advanced dry-run records whether `tryboot.txt` already exists and, when present, its hash. Mutating `prepare` and `overclock` require that file to be absent and refuse to overwrite any pre-existing file, regardless of its contents or apparent origin. Project-owned reset evidence can be reconciled through `reset`; unknown evidence must be inspected explicitly.

Each candidate attempt receives a fresh 256-bit random ownership token. Before the worker can create a remote path, atomic controller state records that token, the exact completed-file hash, the header-reservation hash, and a token-specific quarantine path. The worker creates `tryboot.txt` with shell no-clobber semantics, writes through the held file descriptor, and proves that the pathname still names the same completed, token-bound file. A concurrently appearing operator file is never overwritten. Immediately before reboot, the trigger path again verifies the permanent hash and exact completed candidate.

Controller state is flushed before its atomic rename and the committed state file and containing directory are flushed afterward. Run IDs include a random suffix, target worker paths are isolated by run, and tryboot staging/trigger/cleanup, normal reboot, watchdog repair, permanent apply, and rollback share an atomic `/run` lock. Permanent apply rechecks normal-boot/tryboot absence after the explicit command authorization, inside the locked worker immediately before replacement, and again after its verification boot. The advanced standalone `apply` path additionally requires exact typed confirmation.

Target worker storage is treated as transient across every reboot. One shared controller handshake waits for a changed boot ID, uploads and verifies the run-isolated worker again, and only then permits tryboot, clock, watchdog, cleanup, or health evidence to be collected. Debian may therefore use volatile `/tmp` without assuming that any file survives reboot; Batocera follows the same handshake even though its run directory is persistent.

The controller treats the candidate as possibly live until a separate boot into the untouched permanent configuration proves the tryboot flag clear and the original permanent hash unchanged. Cleanup accepts only the saved completed candidate, exact reservation, or token-header partial file. It uses a no-clobber move to the saved random quarantine path, revalidates ownership after the move, and only then removes it, before the full normal health and watchdog gate. A changed, unowned, ambiguous, or raced file is preserved—at its original or quarantine path—and reported as a recovery failure. An absent live and quarantine path is already clean.

The baseline recovery proof uses the verified stock clocks before any fresh automatic overclock candidate. Stock is the control baseline, not an overclock pass. It must prove the complete tryboot boot, normal recovery, ownership-checked cleanup, and watchdog chain. A failure aborts the run rather than becoming evidence about clock stability.

## Explicit stock reset

`autopioverclock reset TARGET` is the normal stock-reset spelling. Reset is a standalone, noninteractive permanent-config operation, not an option on `run`, `resume`, or `recover`. It takes no tuning, saved-run-selection, confirmation, dependency, watchdog-repair, dry-run, edge, fan-policy, mode, or redaction flags. The command itself is explicit intent; `--yes` is rejected. The older `TARGET reset` order remains a compatibility alias. Both forms require an explicit target.

Reset hashes and audits the root boot config before mutation. A symlink, changing hash, malformed AutoPiOverclock marker block, active `include` directive, or foreign/ambiguous tryboot or quarantine path fails closed. Reset never guesses through included files and never overwrites unknown recovery evidence. Before an accepted replacement it writes and verifies a no-clobber persistent backup; any attributable project tryboot file is backed up before cleanup. Standalone clock/voltage controls remain visible as `# AUTOPIOVERCLOCK-STOCK-DISABLED` comments; the clock directives and markers in one structurally valid managed block are removed while its `[all]` section boundary is retained, and the verified backup keeps the complete original. If the active firmware tryboot flag is set but no live or quarantine path remains, reset claims no ownership and deletes nothing unknown; it prepares the backed-up permanent stock config, forces a normal reboot, and requires the flag to clear. A failed replacement restores the verified backup only while the destination still has a recognized reset hash; unknown concurrent content is preserved. Batocera must restore `/boot` read-only before reporting a result.

Writing a stock-form config is not enough to pass. The controller forces a permanent-config reboot, requires a different boot ID, rechecks the exact expected permanent hash and absent tryboot state, verifies active CPU 2400 MHz, firmware-default V3D 800 or 960 MHz, and zero voltage delta, and checks current throttle/power state plus the active watchdog chain. Reset does not claim the broader display, audio, service, or workload health gates used during tuning. Only its bounded stock-boot sequence may checkpoint `COMPLETE/STOCK_VERIFIED` and emit a reset `PASS` event.

The reset controller uses the existing local per-target and remote mutation locks. It does not stop another controller, issue process-wide kills, or interact with tmux/Byobu; a held lock fails safely. It creates a separate audit run and preserves all earlier local logs, states, summaries, reports, and candidate logs without deletion or truncation.

## Active watchdog proof

The recovery gate does not infer readiness from an arbitrary `config.txt` line. It requires all of the following on the running target:

1. a positive EEPROM `BOOT_WATCHDOG_TIMEOUT`;
2. a positive `watchdog.open_timeout` handed to the active kernel command line;
3. a watchdog character device whose live runtime timeout is positive; and
4. a userspace process with an open file descriptor for that device.

The runtime timeout normally comes from the watchdog's sysfs `timeout` attribute. If that attribute exists in any form but is unreadable, malformed, nonpositive, or not a regular file, the proof fails closed. When the attribute is genuinely absent on ARM64 Batocera, the worker may instead bind the discovered owner PID, process start time, command name, file descriptor, and watchdog device identity; duplicate that already-open descriptor with `pidfd_getfd`; and issue only `WDIOC_GETTIMEOUT`. The probe never opens the device by path and issues no write, keepalive, stop, or configuration ioctl. The duplicate is short-lived but adds a bounded reference-count side effect: if the owner closes concurrently, it can briefly defer the driver's final release, and closing the duplicate can then execute the driver's ordinary close behavior. Any identity change, owner exit, permission denial, unsupported syscall, ioctl failure, or race rejects the proof.

Debian additionally requires an active, nonzero systemd runtime-watchdog setting during discovery and after preparation. When Batocera lacks a complete chain, `prepare` installs the project-owned service and keeper with hash-bound config changes and verified backups. It selects exactly one live IPv4 default gateway as the liveness target, feeds during a 180-second startup grace, requires 180 seconds of continuous loss, and suppresses an endless loop after three recovery reboots in 30 minutes. Foreign project-path content, ambiguous routing, or failed verification stops the installation. Every candidate and normal-boot health gate rechecks the four live conditions above, including the device's current timeout and owner.

## Resume boundaries

Candidate and final-validation operations are checkpointed as explicit substages. Their configured boot loops use range-checked `BOOT_n`/`NORMAL_n` stages: `candidate_boots` is limited to 2–10 and `final_boots` to 3–10. After the ordinary tuning confirmation, resume normalizes any interrupted tryboot first, verifies normal recovery, ownership-checks cleanup, continues completed work, and repeats a boot or stress segment whenever its same-boot evidence was lost. A current schema-8 automatic final CPU, GPU, or combined-endurance `STABILITY_FAILURE` is resumable only after complete normal recovery and empty ownership fields; the reduced target then restarts complete validation. Older state schemas are not mutably resumed through newer safety gates, except for the exact schema-7 automatic final CPU/GPU stress failure whose normal recovery and empty ownership fields are already proved. Legacy combined-endurance failures are not reinterpreted under the newer pair policy.

`telemetry_interval_seconds` is limited to 1–60 seconds and controls target-side sampling during stress. Every sample rechecks temperature, current/new throttle evidence, requested-clock attainment, kernel faults, and supervised workload state; the worker's hard deadline remains separate from the sampling cadence.

An interrupted preflight, failed preflight, or declined tuning confirmation remains readable through `status` and `report`, including any watchdog-repair hashes. It is not mutably resumable: resolve the finding and start a new `run`, because partial dependency or watchdog changes must not become a trusted permanent baseline without a new normal-boot preflight.

## Permanent apply

Permanent apply requires current validation-schema evidence, `PASS`/`COMPLETE` state, and proof that at least 28,800 final-endurance seconds actually completed. An accepted optional edge result requires exactly 86,400 seconds; a rejected edge retains the separately recorded 28,800-second floor. A run whose origin is manual `test` is refused before apply regardless of duration or status. Apply persists the old and proposed hashes, deterministic backup path, boot ID, and recovery intent before remote mutation. Resume reconciles a known old hash by fresh normal-boot health, a known proposed hash by fresh normal-boot health or verified rollback, and refuses to overwrite an unknown hash. Rollback passes the persisted proposed hash into the locked worker and verifies that exact destination hash both on entry and immediately before replacing it with the verified backup.

Fresh and interrupted permanent-apply paths share the same fail-closed gate: current state schema, no saved tryboot ownership/quarantine evidence, a readable cleared live tryboot flag, and an absent `tryboot.txt`. The explicit `overclock` command authorizes application of its own fully validated result after displaying and retaining the exact diff; the standalone advanced `apply` command requires exact typed confirmation, and `--yes` cannot bypass it. A config that already matches the proposal still requires a fresh normal boot and health gate before it is recorded as applied.
