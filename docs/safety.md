# Safety and failure policy

AutoPiOverclock optimizes for recoverability and long-term stability rather than the highest benchmark number.

A candidate fails immediately on any current-boot undervoltage/throttle flag, thermal ceiling event, V3D/DRM fault, kernel panic/internal error/unable-to-handle-kernel report, Oops/BUG/call trace, RCU stall/starvation/timer failure, hung-task warning, USB-device reset, device-offline event, I/O error, buffer error, ext4/btrfs error, nonzero stress process, missing renderer proof, required graphical/audio/service failure, watchdog-chain failure, unexpected reboot, or permanent-config hash change.

`BOOT_FAILURE` and `STABILITY_FAILURE` define a sweep boundary. A lower passing candidate can still proceed to conservative selection. A safely recovered structured or unstructured harness failure receives five complete-gate retries before it remains `HARNESS_FAILURE`. Exhausted `HARNESS_FAILURE`, a valid protected-hash mismatch, and unproved normal recovery abort because none establishes a silicon stability boundary. A controller-only unavailable-hash result is retryable only when complete stock recovery and a fresh exact hash read prove that no recovery uncertainty remains.

Missing or changed audio readiness by itself is a retryable `HARNESS_FAILURE`; it never establishes a CPU or GPU clock boundary.

A lost SSH stream is not itself a stability boundary. Scalar facts, exact files, validated boot/tryboot state, discovery, and permanent hashes receive 30 attempts separated by 10 seconds, while safe read-only/idempotent worker gates receive up to five same-boot attempts. The controller records a changed candidate boot ID before transient worker redeployment, then applies the same proof rule during candidate boot/health, active stress, and post-stress health. Only verified recovery that observes the exact saved candidate boot already changed to a clear permanent-normal boot before the controller issues any reboot can promote an unstructured loss to the appropriate `BOOT_FAILURE` or `STABILITY_FAILURE`. A safely recovered same-boot interruption or structured harness diagnosis can repeat its complete gate five times; exhaustion remains `HARNESS_FAILURE`, and any failure to verify normal recovery remains `RECOVERY_FAILURE`. A valid protected-hash mismatch, changed/foreign tryboot evidence, and an ambiguous permanent mutation stop on first proof and are never hidden by retry.

A maximum observed pass is never called “rock solid.” Full two-domain auto searches CPU in 100 MHz coarse steps and GPU in 50 MHz coarse steps, refining each failure gap in 25 MHz steps to the highest actual pass. CPU must next pass an isolated CPU qualification at stock GPU before GPU search begins; GPU must then pass an isolated GPU qualification at that CPU. The recommended default is two hours for each qualification. A fully recovered `BOOT_FAILURE` or `STABILITY_FAILURE` during a domain qualification lowers only that domain by 25 MHz and repeats its complete saved qualification duration. The selected pair then receives one combined CPU/GPU/I/O final validation for the saved duration. An ambiguous full-mode final clock failure saves that pair as an anchor, then tests CPU-only, GPU-only, and finally paired 25 MHz reductions only while failures remain ambiguous. Exact CPU or GPU evidence from any trial immediately selects only that domain. Each changed domain is requalified before a fresh complete final attempt; if all three trials fail ambiguously, the paired reduction becomes the next anchor and isolation repeats. A successful isolated reduction preserves the other domain's clock, avoiding unnecessary performance loss. One-domain mode lowers and requalifies only its selected domain and stops if exact evidence identifies its held domain. A safely recovered harness failure retries the exact complete gate five times before unresolved harness uncertainty becomes fatal; recovery uncertainty is always fatal. Explicit plans retain their configured list-position backoff. Any genuine failure, even near the end of the final duration, invalidates that attempt: failed-attempt time is never credited. Final clocks are recorded only after every qualification required by the selected mode, one complete accepted endurance and filesystem workload, post-stress health, the configured `final_boots` additional candidate boots and normal recoveries, and a final permanent-config hash check. The approved minimum is three final boot/recovery cycles.

The mutually exclusive `overclock TARGET --cpu-only` and `--gpu-only` modes require an eligible applied AutoPiOverclock result. They sweep and qualify only the selected domain while holding the other at its retained clock after freshly re-proving the live config and tuple. That held clock is a verified baseline, not evidence that its domain is already maximized or the selected-domain boundary. Starting-point flags only trim lower search candidates initially: full mode accepts either or both from stock, while an applied target uses the matching one-domain mode and rejects the opposite start flag. An immediate failure may refine below the requested start in 25 MHz steps. Skipped clocks are never recorded as passes, and no qualification, final-validation, or apply gate is bypassed. Rerunning the same mode and starts resumes only matching retained work.

The 3200 MHz CPU and 1200 MHz GPU/V3D limits are sweep ceilings, not safe recommendations or promises that a target can boot them. Full two-domain configuration-free auto refuses to generate candidates unless the active Pi 5 tuple is CPU 2400 MHz, V3D 800 or 960 MHz, and zero voltage delta, and a before/after-hashed audit of the permanent root config finds no explicit clock or voltage control. A one-domain mode instead requires the latest eligible applied result and proves that the live held-domain clock and permanent config still match its retained evidence. Every mode rejects unsupported boost/turbo/fixed-clock controls, unexpected `*_freq`/`*_freq_min` or `over_voltage*` assignments, snapshot changes, and unbound `include` directives. Candidate clocks remain temporary; only a final current-schema result is written permanently after complete validation and fresh apply gates. Tryboot recovery and every normal stability boundary remain mandatory.

Candidate cooling is isolated to the same temporary artifact. The candidate file inherits the complete protected permanent config—preserving unrelated GPU drivers, overlays, display, audio, PCIe, and other boot requirements—and adds only the project-owned clock/cooling block. By default, every candidate and final-validation tryboot sets the Pi 5 first fan threshold to 0C and all four fan speeds to PWM 255. The worker verifies a detected `pwmfan` device at 255 before health/stress and at every stress telemetry interval; a non-max value, malformed reading, or exposed zero-RPM tachometer is `HARNESS_FAILURE`, never a clock boundary. A missing software-visible PWM device is recorded as `not-detected` so passive and externally controlled cooling remain usable without a false 100% claim. `--no-max-fan` is an explicit new-run opt-out that retains the ordinary fan policy and disables only the PWM-255 assertion; temperature, throttle, clock, and workload gates remain unchanged. The selected policy is persisted and cannot change during resume. Normal recovery, permanent apply, and reset retain the pre-existing permanent fan directives unchanged.

Manual `test TARGET --cpu ... --gpu ... --minutes ...` uses the same candidate ownership, watchdog, maximum-cooling, boot-cycle, health, hash, and normal-recovery gates for one exact clock pair. Both clocks must be normal-or-higher and at least one must be an overclock. A manual pass remains `VALIDATED=0`, creates no automatic recommendation, and is explicitly ineligible for permanent apply regardless of its requested duration. This prevents a user-selected point from bypassing automatic sweep/refinement, every qualification required by the selected mode, combined final endurance, and final post-stress boot requirements.

The interactive progress display is advisory only. Whole-workflow percentage, ETA, and remaining-test counts re-plan from saved phase/index/boundary evidence and never mark a safety gate complete. Worker-reported current-stress elapsed time drives the per-workload countdown; raw telemetry is retained independently. Progress rendering is disabled for non-TTY output so logs and automation receive ordinary newline-delimited evidence rather than terminal-control updates. TTY rendering selects a content-aware compact layout before the right-edge margin, temporarily disables autowrap, and replaces only the current logical row without a newline or vertical cursor movement before parking at column one. Inside tmux, rendering also accounts for the narrowest attached client. The final worker pipeline consumer remains in the controller shell so display state is not lost through a pipeline subshell. Signal and exit handling clear the current row, restore normal terminal wrapping, and suppress any repaint while mandatory normal recovery is running. Arbitrary client-side reflow or a detached client resized between paints can still preserve an older row; that is cosmetic and does not modify raw logs or saved state.

Public automatic tuning has one accepted combined CPU/GPU/I/O final validation, defaulting to 24 hours. A safely recovered harness failure repeats the complete final gate up to five times at the same clocks. A proved ambiguous full-mode clock failure enters the anchored isolation sequence above only while evidence remains ambiguous; exact evidence switches immediately to its identified domain. One-domain mode lowers only its selected domain and stops on exact held-domain evidence. Every attempted pair must independently complete the full saved duration from zero. Exhausted `HARNESS_FAILURE` or any `RECOVERY_FAILURE` remains fatal because neither establishes a safe clock boundary. An eligible completed applied run may start a longer linked final validation only after fresh proof of the exact permanent hash, normal clocks, clear tryboot state, watchdog health, saved graphical/headless mode, and its rollback backup.

## Tryboot file ownership and cleanup

An advanced dry-run records whether `tryboot.txt` already exists and, when present, its hash. Mutating `prepare` and `overclock` require that file to be absent and refuse to overwrite any pre-existing file, regardless of its contents or apparent origin. Project-owned reset evidence can be reconciled through `reset`; unknown evidence must be inspected explicitly.

Each candidate attempt receives a fresh 256-bit random ownership token. Before the worker can create a remote path, atomic controller state records that token, the exact completed-file hash, the header-reservation hash, and a token-specific quarantine path. The worker creates `tryboot.txt` with shell no-clobber semantics, writes through the held file descriptor, and proves that the pathname still names the same completed, token-bound file. A concurrently appearing operator file is never overwritten. Immediately before reboot, the trigger path again verifies the permanent hash and exact completed candidate.

Controller state is flushed before its atomic rename and the committed state file and containing directory are flushed afterward. Run IDs include a random suffix, target worker paths are isolated by run, and tryboot staging/trigger/cleanup, normal reboot, watchdog repair, permanent apply, and rollback share an atomic `/run` lock. Permanent apply rechecks normal-boot/tryboot absence after the explicit command authorization, inside the locked worker immediately before replacement, and again after its verification boot. The advanced standalone `apply` path additionally requires exact typed confirmation.

Target worker storage is treated as transient across every reboot. One shared controller handshake waits for a changed boot ID, uploads and verifies the run-isolated worker again, and only then permits tryboot, clock, watchdog, cleanup, or health evidence to be collected. Debian may therefore use volatile `/tmp` without assuming that any file survives reboot; Batocera follows the same handshake even though its run directory is persistent.

The controller treats the candidate as possibly live until a separate boot into the untouched permanent configuration proves the tryboot flag clear and the original permanent hash unchanged. Cleanup accepts only the saved completed candidate, exact reservation, or token-header partial file. It uses a no-clobber move to the saved random quarantine path, revalidates ownership after the move, and only then removes it, before the full normal health and watchdog gate. A changed, unowned, ambiguous, or raced file is preserved—at its original or quarantine path—and reported as a recovery failure. An absent live and quarantine path is already clean.

The baseline recovery proof uses the verified stock clocks before any fresh automatic overclock candidate. Stock is the control baseline, not an overclock pass. It must prove the complete tryboot boot, normal recovery, ownership-checked cleanup, and watchdog chain. A failure aborts the run rather than becoming evidence about clock stability.

## Explicit stock reset

`autopioverclock reset TARGET` is the only stock-reset spelling. Reset is a standalone, noninteractive permanent-config operation, not an option on `run`, `resume`, or `recover`. It takes no tuning, saved-run-selection, confirmation, dependency, watchdog-repair, dry-run, duration, domain, start-point, fan-policy, mode, or redaction flags. The command itself is explicit intent; `--yes` is rejected, and an explicit target is required.

`autopioverclock restore TARGET` is the bounded repair for a permanent boot config changed outside AutoPiOverclock after a successful apply. It accepts only an optional retained `--run-id` plus transport/output options. The source must still be a current-schema, fully validated, applied result with its exact hash-bound proposed-config artifact, matching target profile, boot paths, storage layout, and clear tryboot ownership. Restore shows the exact replacement diff, creates a fresh no-clobber backup, reuses the serialized permanent apply/rollback protocol, and accepts success only after a normal reboot proves the restored hash, clocks, watchdog, and health. It never deletes older evidence.

Reset hashes and audits the root boot config before mutation. A symlink, changing hash, malformed AutoPiOverclock marker block, active `include` directive, or foreign/ambiguous tryboot or quarantine path fails closed. Reset never guesses through included files and never overwrites unknown recovery evidence. Before an accepted replacement it writes and verifies a no-clobber persistent backup; any attributable project tryboot file is backed up before cleanup. Standalone clock/voltage controls remain visible as `# AUTOPIOVERCLOCK-STOCK-DISABLED` comments; the clock directives and markers in one structurally valid managed block are removed while its `[all]` section boundary is retained, and the verified backup keeps the complete original. If the active firmware tryboot flag is set but no live or quarantine path remains, reset claims no ownership and deletes nothing unknown; it prepares the backed-up permanent stock config, forces a normal reboot, and requires the flag to clear. A failed replacement restores the verified backup only while the destination still has a recognized reset hash; unknown concurrent content is preserved. Batocera must restore `/boot` read-only before reporting a result.

Writing a stock-form config is not enough to pass. The controller forces a permanent-config reboot, requires a different boot ID, rechecks the exact expected permanent hash and absent tryboot state, verifies active CPU 2400 MHz, firmware-default V3D 800 or 960 MHz, and zero voltage delta, and checks current throttle/power state plus the active watchdog chain. Reset does not claim the broader display, audio, service, or workload health gates used during tuning. Only its bounded stock-boot sequence may checkpoint `COMPLETE/STOCK_VERIFIED` and emit a reset `PASS` event.

The reset controller uses the existing local per-target and remote mutation locks. It does not stop another controller, issue process-wide kills, or interact with tmux/Byobu; a held lock fails safely. It creates a separate audit run and preserves all earlier local logs, states, summaries, reports, and candidate logs without deletion or truncation.

## Active watchdog proof

The recovery gate does not infer readiness from an arbitrary `config.txt` line. It requires all of the following on the running target:

1. a positive EEPROM `BOOT_WATCHDOG_TIMEOUT`;
2. a positive `watchdog.open_timeout` handed to the active kernel command line;
3. a watchdog character device whose live runtime timeout is positive; and
4. a userspace process with an open file descriptor for that device.

The runtime timeout normally comes from the watchdog's sysfs `timeout` attribute. If that attribute exists in any form but is unreadable, malformed, nonpositive, or not a regular file, the proof fails closed. When the attribute is genuinely absent on ARM64 Batocera, the worker may instead bind the discovered owner PID, process start time, command name, file descriptor, and watchdog device identity; duplicate that already-open descriptor with `pidfd_getfd`; and issue only `WDIOC_GETTIMEOUT`. The probe never opens the device by path and issues no write, keepalive, stop, or configuration ioctl. The duplicate is short-lived but adds a bounded reference-count side effect: if the owner closes concurrently, it can briefly defer the driver's final release, and closing the duplicate can then execute the driver's ordinary close behavior. Any identity change, owner exit, permission denial, unsupported syscall, ioctl failure, or race rejects the proof.

Debian additionally requires an active, nonzero systemd runtime-watchdog setting during discovery and after preparation. When Batocera lacks a complete chain, `prepare` installs the project-owned service and keeper with hash-bound config changes and verified backups. It selects exactly one live IPv4 default gateway as the liveness target, feeds during a 180-second startup grace, requires 180 seconds of continuous loss, and suppresses an endless loop after three recovery reboots in 30 minutes. Foreign project-path content, ambiguous routing, or failed verification stops the installation. Every candidate and normal-boot health gate rechecks the four live conditions above, including the device's current timeout and owner.

## Resume boundaries

Candidate, qualification, and final-validation operations are checkpointed as explicit substages. Their configured boot loops use range-checked `BOOT_n`/`NORMAL_n` stages: `candidate_boots` is limited to 2–10 and `final_boots` to 3–10. After tuning begins, resume normalizes any interrupted tryboot first, verifies normal recovery, ownership-checks cleanup, continues completed work, and repeats a boot or stress segment whenever its same-boot evidence was lost. Every mutating/recovery command remains in read-only SSH monitoring after its ordinary timeout and issues no repeated reboot; operator interruption leaves the checkpoint resumable. A recovered clock backoff is accepted only after complete normal recovery and empty ownership fields. Current state binds the exact qualification and final durations, their `default`/`custom` policy labels, selected domain mode, starting points, exact qualification identities, and ordered anchor/isolation history. A requested `--restart-from` checkpoint can update the duration plan only after normal recovery and only before final validation has started; clocks are derived from retained sweep/backoff state, never supplied as replacement CLI values. Later checkpoints require exact saved prerequisite qualifications. A completed applied run can start only a longer linked final validation using its retained clocks and verified stock rollback backup. If that linked combined test proves a clock boundary and full stock recovery clears all owned tryboot evidence, the rejected clocks stay unapplied. A genuinely ambiguous full-mode failure begins CPU-only, GPU-only, then paired 25 MHz isolation and advances through that sequence only while evidence remains ambiguous; exact CPU or GPU evidence switches immediately to that domain. One-domain mode steps down and requalifies only its selected domain and stops on exact evidence against the held domain. Every trial starts a fresh full requested-duration final validation. Plain resume performs a fresh stock-health proof before adopting a retained boundary. Eligible exact controller-only unavailable-hash state is adopted only after stock health and the protected hash are freshly proved. Older eligible states are migrated conservatively; preflight, foreign, mismatched, or ambiguous state remains non-resumable.

`telemetry_interval_seconds` is limited to 1–60 seconds and controls target-side sampling during stress. Every sample rechecks temperature, current/new throttle evidence, requested-clock attainment, kernel faults, and supervised workload state; the worker's hard deadline remains separate from the sampling cadence. Workload and Bash supervisor clocks are independent, so only a clean exit within 0.1% of the requested duration—bounded to 3–30 seconds—is accepted as complete. Earlier clean exits and every nonzero exit remain failures.

An interrupted preflight, failed preflight, or declined tuning confirmation remains readable through `status`, `summary`, and `report`, including any watchdog-repair hashes. `status` and `summary` use only short read-only SSH observations and do not acquire the controller lock or change boot configuration/project run artifacts. The interrupted preflight is not mutably resumable: resolve the finding and start a new `run`, because partial dependency or watchdog changes must not become a trusted permanent baseline without a new normal-boot preflight.

## Permanent apply

Permanent apply requires current validation-schema evidence, `PASS`/`COMPLETE` state, and proof that the completed endurance seconds exactly match the saved final duration. The recommended policy is 2 hours per qualification and one 24-hour final validation; custom whole-hour values from 1–168 are labeled `custom`, and shorter values deliberately trade confidence for time without bypassing any other gate. A run whose origin is manual `test` is refused before apply regardless of duration or status. Apply persists the old and proposed hashes, deterministic backup path, boot ID, and recovery intent before remote mutation. Resume reconciles a known old hash by fresh normal-boot health, a known proposed hash by fresh normal-boot health or verified rollback, and refuses to overwrite an unknown hash. Rollback passes the persisted proposed hash into the locked worker and verifies that exact destination hash both on entry and immediately before replacing it with the verified backup.

Fresh and interrupted permanent-apply paths share the same fail-closed gate: current state schema, no saved tryboot ownership/quarantine evidence, a readable cleared live tryboot flag, and an absent `tryboot.txt`. The explicit `overclock` command authorizes application of its own fully validated result after displaying and retaining the exact diff; the standalone advanced `apply` command requires exact typed confirmation, and `--yes` cannot bypass it. A config that already matches the proposal still requires a fresh normal boot and health gate before it is recorded as applied.
