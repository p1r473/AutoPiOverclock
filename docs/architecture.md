# Architecture

The controller owns policy, state, logging, candidate order, recovery decisions, and reporting. A small standalone worker performs privileged target operations. Workers emit structured `APO_DATA` and `APO_RESULT` records so controller-side classification does not depend only on prose greps.

## Controller layers

- `common.sh`: validation, quoting, target parsing, backoff.
- `config.sh`: strict non-executable configuration.
- `history.sh`: strict retained-state screening, clear-domain and ambiguous-pair frontier extraction, immutable plan resolution, and human-readable ledger generation.
- `state.sh`: durable, atomic base64-encoded resume state with run and validation schema versions.
- `logging.sh`: flat immutable run artifacts and latest symlinks.
- `progress.sh`: TTY-only dynamic whole-workflow estimates and second-level current-stress display; raw telemetry remains authoritative.
- `ssh.sh`: `command ssh -F /dev/null` transport, separate-controller boot-ID proof, root/sudo wrapper, 30-attempt validated reads, bounded reboot-start confirmation, and persistent reboot monitoring.
- `detect.sh`: OS/profile discovery, dependency preflight, active watchdog-chain proof, and the shared post-reboot worker/helper handshake.
- `remote_job.sh`: token-bound target stress launch, boot-monotonic fixed-deadline supervision, reconnect, retained-result verification, and reboot attribution.
- `recovery.sh`: tryboot trigger, pre-worker boot-ID observation, bounded transient-gate retries, strict network-watchdog continuation, and normal return.
- `reset.sh`: standalone explicit-target reset orchestration, persistent-backup evidence, permanent reboot, and verified-stock completion.
- `candidates.sh`: resumable candidate/manual-test substages, refinement, qualification, final validation, and backoff.
- `apply.sh`: current-schema saved-duration eligibility, exact diff, explicit overclock authorization or standalone typed confirmation, persisted backup plan, normal-reboot health, and rollback.

For full `--mode auto` without an explicit configuration, each worker hashes the permanent root config before and after auditing all documented clock/voltage control families. Snapshot changes and explicit tuning controls are reported, and any `include` directive fails closed because the existing protected permanent hash covers only the root config. `config.sh` defers candidate resolution until `detect.sh` has verified both that provenance evidence and the active stock tuple (2400 MHz CPU, supported 800/960 MHz firmware-stock V3D, zero voltage delta). A one-domain run instead requires an eligible applied AutoPiOverclock result and binds the held domain to its retained clocks after freshly re-proving the live config and tuple. Every public `overclock` invocation creates a new run. `history.sh` ignores and preserves older or missing schemas before requiring current metadata, ignores unrelated or no-evidence operations, fully validates compatible current-schema evidence-bearing automatic-run states, fails closed on malformed current-schema evidence, or honors the explicit history-free policy. It derives advisory per-domain ceilings and nondominated ambiguous-pair frontiers. `config.sh` binds those separately from user bounds and resolutions. Without a useful retained limit or explicit maximum, a domain gets its normal forward coarse plan. A clear retained ceiling selects a reverse plan from that value. When a full run has no manual maxima, the newest nondominated ambiguous pair instead becomes the automatic reverse-search anchor, and the failed pair's first CPU-lowered isolation branch is derived before candidate generation. A user-supplied maximum is the authoritative reverse-search ceiling; conflicting retained evidence produces a warning but does not rewrite it. CPU coarse movement is `max(100, CPU resolution)` MHz and GPU coarse movement is `max(50, GPU resolution)` MHz, while independently saved CPU/GPU resolutions default to 25 MHz and accept whole-MHz values from 1 through 1000 for refinement and automatic reductions. Explicit minima are hard floors for every search and backoff route. A history-enabled plan creates or materially refreshes the audit ledger as needed and emits the retained ceilings, automatic pair anchor, first isolated pair, requested maxima, selected direction, warning state, evidence, and ledger path; an unchanged ledger is not replaced. `candidates.sh` checkpoints forward or reverse coarse positions, resolution-sized refinement, highest proved passes, exact qualification identities, immutable bounds/resolutions/history choices, and ordered qualification backoff or final-pair isolation. Explicit configuration files bypass stock-gated generation and remain authoritative.

## Target profiles

Raspberry Pi OS, Debian, and supported Ubuntu Pi layouts use `stress-ng`, systemd hardware-watchdog ownership, and normal writable boot configuration. Screenless systems automatically use headless health gates: no display/audio identity is required, but the actual V3D render node and a usable GPU stress route remain mandatory. The worker uses explicit `--gpu-devnode` routing when available and permits the older default-device form only when exactly one render node exists and it is the discovered V3D node. Batocera uses an all-core OpenSSL SHA-256 benchmark with one 1 MiB block for CPU load; the block size keeps multi-day Pi 5 runs below OpenSSL's signed per-worker operation counter while preserving the requested elapsed stress duration. It uses a persistent portable glmark2 payload for GPU load, an OS-specific read-only `/boot` remount cycle, and a reboot syscall for tryboot. Both profiles require an already-working hardware-watchdog recovery chain. If a recognized network watcher already exists, discovery records its liveness target, installed hashes, and active state for later read-only reboot proof. AutoPiOverclock never installs or configures either watchdog type.

Each run receives a collision-resistant ID and its own target-side worker directory. Debian uses `/tmp` and never assumes that directory survives a target reboot; Batocera uses persistent userdata but follows the same upload handshake. The controller installs both the worker and the detached-job helper and re-verifies them after every changed target boot ID. A timed gate creates a unique job directory containing a data-only manifest, supervisor identity, worker output, and atomic completion metadata. The job is tied to its run token, specification hash, source boot ID, duration, and exact worker path. Boot-critical mutations on a target, including tryboot staging, triggering and cleanup, normal reboot, permanent apply, and rollback, share one atomic target lock. A controller can therefore observe another active run, but it cannot overlap that run's recovery-sensitive operation.

Every candidate attempt also receives a fresh 256-bit ownership token. The controller durably checkpoints the token, reservation hash, completed-file hash, and quarantine path before the worker may create `tryboot.txt`. The worker uses no-clobber creation and held-descriptor checks, repeats exact verification immediately before reboot, and removes the file only after verified normal recovery through a no-clobber quarantine-and-revalidation step. Unknown or raced evidence is preserved and fails closed.

## State phases

```text
PREPARE → TRYBOOT_PROOF (displayed as baseline safety proof) → GPU_SMOKE → CPU_SWEEP(forward or reverse)/refinement
        → CPU_QUALIFICATION(saved duration, stock GPU) → GPU_SWEEP(forward or reverse)/refinement
        → GPU_QUALIFICATION(saved duration, qualified CPU)
        → COMBINED_FINAL(saved final duration) → COMPLETE

PREPARE → TRYBOOT_PROOF (displayed as baseline safety proof) → GPU_SMOKE → MANUAL_TEST(one exact CPU/GPU pair) → COMPLETE
```

Skipped explicit-plan domains are bypassed. Within each candidate, state records the candidate identity and a generic `BOOT_n`/`NORMAL_n` substage across the configured `candidate_boots` cycles, followed by the stress boot, stress, post-stress health, and final normal recovery. Automatic search directions, coarse indices, refinement brackets, highest passes, exact saved-duration CPU/GPU qualification identities, requested hard minima and authoritative maxima, retained ceilings, per-domain resolutions, saved history policy/provenance, and ordered final anchor/isolation history are resumable. A reverse search begins at its exact ceiling, descends by the domain's coarse step until a pass brackets the closest failure, then refines that bracket toward the ceiling at the domain resolution. A forward search ascends normally until it establishes the corresponding pass/fail bracket and refines it at the same resolution. In full mode, CPU search is isolated at protected baseline GPU; after CPU qualification, GPU search is isolated at the qualified CPU. One-domain mode bypasses the unselected sweep and qualification while holding that domain at the freshly re-proved clock from an eligible applied result.

Every automatic run seeks one accepted saved-duration combined CPU/GPU/I/O final workload, return to normal, the configured `final_boots` post-stress `BOOT_n`/`NORMAL_n` cycles, and final hash verification. CPU-specific evidence lowers only CPU by the saved CPU resolution, and GPU-specific evidence lowers only GPU by the saved GPU resolution. A proved ambiguous full-mode failure saves the pair as its anchor and tries a CPU-only reduction. Only continued ambiguous evidence advances to restored CPU with a GPU-only reduction, then to both reductions; exact evidence from any trial immediately follows its identified domain, while three ambiguous failures advance the paired reduction to the next anchor. Each changed domain is requalified before its fresh full final attempt. A required move below a hard minimum terminates the run with that floor identified. One-domain mode changes only its selected domain and stops if exact evidence identifies the held domain. Its final reduction may land on the inherited applied pair: the rejection is retained, that selected domain is requalified, and a fresh complete final runs from zero; the held domain never changes and neither clock goes below the source. Every adjusted pair restarts the complete saved final duration, so a genuine failure near the end receives no elapsed-time credit. The public defaults are 2 hours per qualification and 48 hours for final validation.

A completed applied result can request a longer fresh final through a linked run: the exact saved clocks, per-domain resolutions, hard floors, and verified pre-apply stock backup are bound before rollback. A fully recovered ambiguous full-mode boot/stability rejection applies the same anchored CPU-only, GPU-only, then paired resolution-sized isolation sequence only while evidence remains ambiguous; exact evidence switches immediately to its identified domain. A one-domain rejection changes only its selected domain and stops on exact held-domain evidence; it may return exactly to the inherited source pair for requalification and a fresh full final, but never below it. Each adjusted pair repeats the required qualification and starts a fresh full requested-duration final validation; a hard-floor conflict or uncertainty stops with stock active. Source artifacts remain immutable, each linked apply has its own backup, and the source validation mode is retained exactly: graphical remains graphical, and a screenless headless run remains headless.

`resume` continues only the selected saved run; omitting `--run-id` selects the latest eligible operation. A fresh `overclock` never enters this continuation path. Before timed stress launch, the controller checkpoints the exact detached-job identity. The target starts it with `nohup` and a separate session, enforces the requested duration plus a 300-second shutdown grace, and atomically records the output size, SHA-256 hash, exit status, and end time. A dropped SSH stream therefore does not terminate stress. The controller reconnects indefinitely, rejects duplicate or mismatched ownership, discards a partial protocol record only when SSH itself reports transport loss, and fetches completed output only after exact size/hash verification. If the controller restarts, `resume` finds the saved job before normalizing tryboot and reattaches to that same job. If the target reboots, the helper cannot survive; the controller must classify the changed boot before making any clock decision.

A target reboot is called network-watchdog-caused only when the active profile proves one fresh event from a recognized watcher that was already present at discovery. Proof binds the exact saved source boot, current boot, configured liveness target, event identity and time, unchanged installed hashes, exact active service, and matching prepared, committed, and next-boot-accepted durable records. The watcher must withdraw or invalidate pending intent if its requested reset does not begin inside a bounded interval. Complete proof preserves only workload elapsed time reported in the last target telemetry checkpoint at or before that request. A new detached segment runs the exact uncredited remainder at the same clocks without consuming the ordinary five-retry harness budget. No wall-clock or SSH-outage time is credited. Missing, stale, late, mismatched, or contradictory proof discards partial time and permits one conservative full same-clock replay. A second unattributed reboot of the identical gate may enter ordinary stability classification only after complete protected normal recovery. Safe read-only/idempotent worker gates still get up to five same-boot attempts, and other safely recovered harness failures still receive five complete-gate retries. A primary normal-return handshake timeout remains provisional and cannot lower clocks without complete recovery evidence. A hard-floor conflict, valid protected-hash mismatch, foreign ownership, or ambiguous mutation bypasses retries and stops.

The controller's interactive bar derives total remaining work from saved sweep indices, dynamically discovered boundaries/refinement ladders, qualification state, final backoff/isolation state, and the single final validation. Reboot/SSH segments use bounded estimates, so total percentage/ETA and test counts are explicitly approximate and may increase after a failure adds fresh qualification and final work. Target heartbeats move the current countdown every second. During an SSH outage the same logical row becomes a rotating reconnect indicator with its own seconds counter; normal progress resumes after exact job ownership and boot identity are reconciled. TTY rendering consumes telemetry for one in-place display while duplicating unmodified worker lines into the candidate and main logs; redirected execution prints them normally. Each paint replaces only the current logical row, parks at column one, and uses no newline or vertical cursor movement, minimizing controller-generated row stacking. In tmux, the renderer also uses the narrowest attached client's width. Arbitrary client-side reflow or a detached client resized between paints can still preserve an earlier row; retained logs and state are unaffected. The final pipeline consumer runs in the controller shell so terminal and state ownership remain synchronized. Cleanup marks rendering shut down before clearing the current row so subsequent recovery logging cannot repaint a stale bar.

Controller policy passes `telemetry_interval_seconds` and the saved normal/candidate cooling context to each target worker. Candidate tryboot rendering adds a test-only Pi 5 maximum-fan block by default; `--no-max-fan` selects the normal context for a new run and is then immutable across resume. Workers sample and log temperature, throttle state, active clocks, detected `pwmfan` PWM/RPM state, new kernel errors, and supervised stress processes at the bounded cadence. The outer target job independently enforces the overall deadline even if the controller is absent. Under the default policy, a detected fan that is not at PWM 255 aborts as harness uncertainty. Normal and permanent clock rendering never imports the candidate fan block, so pre-existing fan directives return automatically after every normal boot and remain in the applied result.

An interrupted `PREPARE` is different: dependency installation may have only partially changed the target. Its state remains available to `status`, `summary`, and `report`, but mutating resume is refused so the controller cannot silently adopt an unverified target as its new baseline.

The `reset TARGET` path does not consume or erase a prior tuning run. It allocates a standalone audit run, acquires the same controller/target mutation locks, rejects foreign tryboot evidence and unbound includes, checkpoints the expected old/new hashes and no-clobber persistent backup, then performs an ordinary permanent-config reboot. Completion requires a changed boot ID, the exact new hash, no tryboot state, verified firmware-stock clocks, clear current throttle/power state, and the active watchdog chain. It does not claim tuning's broader health gates. Terminal multiplexers and unrelated controller processes are outside its authority. Only the command-first form is accepted, and its target is mandatory.
